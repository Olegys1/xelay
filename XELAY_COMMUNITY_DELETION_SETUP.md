# Видалення власних запитань і відповідей

## Налаштування Supabase

1. Відкрийте файл `supabase/migrations/202609300004_community_deletion.sql` і скопіюйте весь його вміст.
2. У проєкті Supabase відкрийте **SQL Editor** → **New query**, вставте SQL і натисніть **Run**.
3. Дочекайтеся успішного завершення запиту. Потім опублікуйте оновлений інтерфейс через звичний GitHub/Vercel процес та оновіть сторінку.

Застосуйте SQL перед оновленням інтерфейсу. Нова версія рахує відповіді на сервері; якщо стара відкрита вкладка спробує записати свій застарілий лічильник, база замінить його фактичною кількістю відповідей. Старі базові міграції повторювати не потрібно.

База повинна вже містити `public.questions` зі стовпцями `id`, `user_id`, `answers_count` і `public.answers` зі стовпцями `id`, `user_id`, `question_id`. Первинної схеми цих таблиць у репозиторії немає. Міграція перевіряє необхідні стовпці й підтримує ідентифікатори TEXT та UUID без зміни їхнього типу.

## Що змінюється

Користувач може видалити лише власне запитання або власну відповідь. Права перевіряються на сервері, незалежно від видимості кнопки в інтерфейсі. Видалення остаточне.

Видалення запитання прибирає всі його відповіді, зокрема відповіді інших учасників. Пов’язані записи зображень, обговорення відповідей, старі коментарі запитання та сповіщення також видаляються. Необов’язкові таблиці й стовпці перевіряються перед очищенням.

Видалення окремої відповіді прибирає її записи зображень, обговорення та сповіщення, а інші відповіді залишаються. Сервер повертає актуальну кількість відповідей. Додавання й видалення відповіді автоматично перераховують `questions.answers_count`; міграція також виправляє наявні лічильники за фактичними даними.

Для відомих пов’язаних таблиць `question_images`, `answer_images`, `answer_discussions`, `question_comments` і `notifications` додається перевірка існування запитання та відповіді під час вставки або зміни їхніх посилань. Якщо запис створюється одночасно з видаленням публікації, база або завершує його створення до очищення, або відхиляє вставку після видалення. Це працює й без зовнішніх ключів у старій схемі. Якщо запис містить обидва посилання, відповідь повинна належати вказаному запитанню. Сповіщення інших типів без цих посилань проходять без додаткової перевірки.

Інтерфейс використовує `xelay_delete_own_question(p_question_id text)` і `xelay_delete_own_answer(p_answer_id text)`. Друга функція повертає число. Пряме видалення таблиць для звичайних користувачів вимкнено; наявні права привілейованого доступу Supabase не змінюються.

## Якщо Supabase повернув помилку

SQL виконується однією транзакцією. Якщо налаштування завершилося помилкою, його зміни не застосовуються. Якщо під час видалення виявлено додатковий зв’язок старої схеми, очищення і видалення відкочуються разом: частково видалених записів не буде. Збережіть текст помилки, щоб додати конкретну залежність у міграцію.

Міграція не видаляє й не замінює невідомі старі тригери. Новий перерахунок працює наприкінці транзакції, після звичайних тригерів вставки й видалення.

Для видалення запитання використовуйте кнопку в Xelay: її серверна функція спочатку прибирає відповіді, а потім запитання. Пряме видалення запитання через Table Editor може конфліктувати зі старим тригером, якщо той змінює лічильник під час видалення відповіді. У такому разі потрібна перевірка конкретного старого тригера; нова міграція його не вимикає автоматично.

Файли в **Supabase Storage** автоматично не видаляються. Видаляються лише пов’язані записи в таблицях. Старі прямі посилання на файли можуть залишатися дійсними; прибирання самого сховища потребує окремого виклику Storage API з перевіркою власника та інших посилань на файл.

Міграцію підготовлено локально; у вашому Supabase її не запускали.
