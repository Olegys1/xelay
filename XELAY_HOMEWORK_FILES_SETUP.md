# Файли й кілька посилань до домашнього завдання

До запису для конкретної дати заняття староста може додати до **10 файлів**
і **10 посилань**. Максимальний розмір одного файлу — **20 МіБ**
(20 971 520 байтів). Тему або текст можна залишити порожніми, якщо є файл
чи посилання. Запис не повторюється на інші дати заняття.

## Застосування

1. Застосуйте попередні міграції, зокрема
   `supabase/migrations/202609300001_participant_billing.sql` і
   `supabase/migrations/202610010001_lesson_topics.sql`.
2. Застосуйте повністю
   `supabase/migrations/202610010002_homework_resources.sql` звичайним
   процесом міграцій або через SQL Editor потрібного проєкту Supabase.
   Міграція створює приватний bucket `xelay-homework-files`, його політики
   доступу, колонки та перевірки. Її можна застосувати повторно.
3. Опублікуйте оновлений сайт. Староста обирає дату, відкриває форму
   «Додати тему / ДЗ» або «Редагувати», додає посилання та файли й зберігає запис. Учасники групи
   бачать матеріали під відповідним заняттям. Попередні записи та їхні
   одиночні посилання зберігаються.

Локально пройшли перевірка TypeScript, production-збірка та 82 перевірки
валідації, збереження, вибору файлів, завантаження, очищення й стану редактора.
У перевірках Storage та запити до бази замінені імітаціями; живих запитів
і змін бази не було. Міграцію не виконано в локальній або робочій базі.
Фактичну роботу Storage, RLS та сповіщень ще потрібно підтвердити після
застосування в середовищі розробки або staging.

## Права доступу

Завантажувати файли й змінювати матеріали може поточний староста групи
з чинним правом редагування. Правило збігається з чинним
`xelay_group_billing_status.can_edit`: староста та активна ліцензія групи,
або староста, коли вимогу оплати груп ще не активували.
Міграція не вимикає перевірку ліцензії й не видає ліцензій.

Чинні політики видалення записів домашнього завдання та пар у базі
зберігаються; сайт дозволяє це старості з правом редагування. Нове
видалення об’єктів Storage окремо перевіряє право редагування. Якщо
ліцензію відкликали до завершення очищення, файли може прибрати серверний
процес або оператор із service role через Storage API.

Приватний файл доступний прийнятому учаснику тільки тоді, коли його шлях
вже є в збереженому записі цієї групи. Запрошені, відхилені та видалені
учасники не отримують доступу. Поточний староста може читати збережені
матеріали своєї групи та власні завантажені чернетки. Сам шлях до файлу
не є загальнодоступним URL. Посилання для доступу до файлів слід отримувати
через авторизований Storage API; тимчасовий signed URL не зберігається
в домашньому завданні. Кнопка завантаження отримує signed URL на 60 секунд
і передає оригінальну назву файлу. Уже видане тимчасове посилання залишається
придатним до завершення строку дії, тому його не слід поширювати.
Параметри описані в
[документації Supabase про signed URL](https://supabase.com/docs/reference/javascript/file-buckets-createsignedurl).

Політики Storage містять обмежувальні перевірки для цього bucket, тому
широкі попередні політики інших функцій не відкривають доступ до файлів
домашнього завдання. Інші bucket зберігають свої правила. Перезапис,
переміщення через UPDATE та `upsert: true` для цього bucket заборонені.

## Формат даних

`public.study_group_homework` отримує два поля JSONB з типовим значенням
`[]`, обидва `NOT NULL`:

- `resource_links`: до 10 рядків HTTP(S), кожен до 2048 символів, без
  пробілів. Поле `url` відображає перше посилання нового масиву для
  сумісності. Якщо нового масиву немає, старе `url` залишається читабельним
  і не потребує перезапису всіх попередніх рядків.
- `attachments`: до 10 об’єктів з рівно чотирма полями: `storage_path`,
  `file_name`, `mime_type`, `file_size`. Розмір — ціле число байтів від 1
  до 20 971 520; відображувана назва — до 255 символів із дозволеним
  розширенням, що відповідає MIME; MIME — до 120.
  Повторення того самого шляху в одному записі заборонене.

Приклад вкладення:

```json
{
  "storage_path": "<group UUID>/<representative UUID>/<random UUID>-homework.pdf",
  "file_name": "Домашнє завдання.pdf",
  "mime_type": "application/pdf",
  "file_size": 125600
}
```

Фактичний шлях містить UUID групи та поточного користувача, потім випадковий
UUID, дефіс і очищену назву файлу ASCII до 180 символів разом із розширенням.
Очищена назва починається літерою або цифрою; решта символів — літери,
цифри, крапка, підкреслення або дефіс. Оригінальну українську назву можна
залишити в `file_name`. Шляхи іншої групи або нові файли іншого користувача
не проходять перевірку.

Перед збереженням SQL перевіряє, що кожен файл існує у
`storage.objects` саме в bucket `xelay-homework-files`, а його фактичні
`metadata.size` та `metadata.mimetype` збігаються з описом вкладення.
Опис файлу не може замінити завантаження.

Якщо старосту змінили, новий староста може зберігати незмінені наявні
описи файлів попереднього старости й додавати власні. Учасники продовжують
читати прикріплені матеріали. Очищення старих файлів із каталогів іншого
користувача потребує серверного процесу з service role через Storage API.

## Дозволені типи файлів

Клієнт передає узгоджений `contentType` під час завантаження й той самий
`mime_type` у JSONB. Розширення та MIME повинні відповідати таблиці:

| Розширення | MIME |
| --- | --- |
| `.pdf` | `application/pdf` |
| `.doc` | `application/msword` |
| `.docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| `.xls` | `application/vnd.ms-excel` |
| `.xlsx` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| `.ppt` | `application/vnd.ms-powerpoint` |
| `.pptx` | `application/vnd.openxmlformats-officedocument.presentationml.presentation` |
| `.txt` | `text/plain` |
| `.csv` | `text/csv` |
| `.jpg`, `.jpeg` | `image/jpeg` |
| `.png` | `image/png` |
| `.webp` | `image/webp` |
| `.zip` | `application/zip` або `application/x-zip-compressed` |

## Збереження та очищення

Клієнт спочатку перевіряє форму й послідовно завантажує нові файли через
Storage API з `upsert: false`. Після завершення всіх завантажень він
зберігає всі посилання та описи файлів одним INSERT або UPDATE домашнього
завдання. Зміна файлів або посилань викликає чинне сповіщення
`group_homework` прийнятим учасникам; предмет, дата та тема залишаються
в повідомленні. Завантаження чернетки не створює сповіщення.

Щоб прибрати файл, клієнт спочатку успішно зберігає запис без його опису,
а вже потім викликає `storage.from('xelay-homework-files').remove(...)`.
Після видалення всього запису порядок такий самий: спочатку рядок у базі,
потім непотрібні файли. Видаляти можна тільки власні файли поточного
старости з правом редагування і лише якщо жоден запис домашнього завдання
взагалі не посилається на цей шлях. Повторне використання файлу на іншій
даті захищає його від передчасного видалення.

Перевірка збереження та перевірка видалення використовують спільне
блокування для кожного шляху. Після очікування видалення повторно читає
посилання свіжим запитом, щоб одночасне збереження запису не залишило
опис уже видаленого файлу. Авторизація перевіряється до блокування.
Це правило спирається на стандартну ізоляцію PostgreSQL `READ COMMITTED`.
Для власного серверного очищення видаляйте файли окремими викликами:
масове видалення може взяти блокування в іншому порядку та спричинити
припинення одного з паралельних запитів через взаємне блокування. Клієнт
видаляє файли послідовно, по одному об’єкту в запиті. Посилання захищені,
а невдале очищення можна повторити.

Якщо завантаження або збереження не завершилися, клієнт намагається
прибрати лише щойно завантажені чернетки. Перевірка посилань у Storage
також захищає файл, коли запис уже збережений, але відповідь на збереження
загубилася. Помилка очищення не повинна скасовувати вже збережений запис.

Видалення повторюваної пари каскадно видаляє її записи домашнього
завдання. Для очищення клієнт до видалення пари збирає шляхи з її записів,
видаляє пару й після успіху прибирає власні файли через Storage API.
Перерване закриттям вкладки збереження, пряме видалення рядків у базі,
видалення всієї групи та файли попереднього старости можуть залишити
неприкріплені об’єкти. Автоматичний фоновий збирач таких об’єктів до цієї
зміни не входить; за потреби додайте окреме серверне очищення після
перевірки всіх посилань та достатнього часу для незавершених завантажень.

Не видаляйте рядки з `storage.objects` SQL-командою: це не видаляє сам
об’єкт у сховищі й залишає його оплату. Очищення має проходити через
Storage API, як описано в
[документації Supabase про схему Storage](https://supabase.com/docs/guides/storage/schema/design).

Завантаження Storage і збереження рядка — дві окремі операції. RLS,
перевірка існування файлу й заборона видалення прикріплених файлів
захищають звичайний потік збереження; аварійне очищення та облік
неприкріплених об’єктів залишаються окремою серверною задачею.
