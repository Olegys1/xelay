# Місця для доповнювачів: серверний контракт

Підготовлена міграція: `supabase/migrations/202610220002_seminar_supplement_capacity.sql`.
Цей документ не підтверджує її застосування до робочої бази.

## Дані та сумісність

| Поле | Тип | Значення |
| --- | --- | --- |
| `study_groups.supplement_capacity` | `integer NOT NULL DEFAULT 3` | Налаштування групи для **нових** питань, від 0 до 30 включно. |
| `study_group_seminar_questions.supplement_capacity` | `integer NOT NULL DEFAULT 3` | Збережена кількість місць конкретного питання, від 0 до 30 включно. |

Існуючі групи й питання отримують 3. Міграція не змінює бронювання, ID,
порядок питань, зміст, дати або версії семінарів. Додавання константного
значення за замовчуванням не запускає тригери зміни питань чи сповіщень.

0 означає, що на питання не можна записатися доповнювачем. Це не впливає
на основних доповідачів, команди або бронювання питань. Для форматів
`questions` і `booking` поле зберігається в записі питання, але роль
`supplement` доступна лише в `questions`, як і раніше.

## Читання

Учасники читають налаштування групи через наявний RLS-запит:

```ts
supabase.from('study_groups').select('supplement_capacity').eq('id', groupId).single()
```

До наявного select питань потрібно додати `supplement_capacity`.
Запит `xelay_classroom_seminars(p_course_id, p_group_id)` повертає
`supplement_capacity` групи на верхньому рівні JSON; кожен елемент `questions`
містить власне однойменне поле. Інші існуючі запити, що повертають питання
через `to_jsonb(q)`, також автоматично включають збережене поле.
Чинні перевірки членства, прийнятого підключення викладача й предмета
залишаються на місці; окремого публічного доступу не додається.

## Зміна налаштування групи

```ts
supabase.rpc('xelay_set_seminar_supplement_capacity', {
  p_group_id: groupId,
  p_capacity: 5,
})
```

Відповідь: ціле число збереженого налаштування, наприклад `5`.
Параметр обов'язковий, 0..30. Дробове значення не є значенням SQL-типу
`integer` і не повинно надсилатися клієнтом.

RPC використовує `xelay_lock_seminar_group(group_id, true)` та наявне право
групи **`seminars`**. Доступ мають староста або прийнятий заступник із цим
правом. Статус адміністратора платформи сам по собі не додає права
редагувати навчальні дані. Викладач із доступом до предмета може редагувати
місця питання через свій наявний редактор, але цей доступ не дає права
змінювати налаштування всієї групи.

Зміна налаштування не переписує вже створені питання й нікого не виписує.
Наприклад, зменшення налаштування групи з 3 до 0 допустиме навіть за
наявності старих записів: їхні власні ліміти залишаються 3.

## Збереження питання

Імена й сигнатури наявних RPC не змінюються:

* `xelay_save_seminar(...)` та його обгортка з ресурсами;
* `xelay_classroom_mutate('save_seminar', payload)` через наявний
  `xelay_classroom_seminar_mutate` і захист повторних запитів.

У кожному елементі `questions` / `p_questions` дозволене додаткове поле:

```json
{
  "id": "uuid-існуючого-питання",
  "body": "Питання до семінару",
  "primary_capacity": 1,
  "supplement_capacity": 5
}
```

`id` залишається необов'язковим відповідно до чинного шляху створення.
Правила вибору кількості місць:

1. Явне ціле JSON-число `supplement_capacity` у межах 0..30 має пріоритет.
2. Якщо поле відсутнє й питання вже існує, зберігається його власне значення.
3. Якщо поле відсутнє й питання нове, береться актуальне налаштування групи
   під блокуванням збереження.

Отже, старі клієнти можуть зберігати питання без нового поля та не скидають
індивідуальні налаштування. JSON `null`, рядок, дробове або від'ємне число
невалідні. Клієнт має завантажувати збережене значення при редагуванні;
зміна налаштування групи не повинна масово змінювати його в редакторі.

## Бронювання та захист записів

`xelay_reserve_seminar(p_seminar_id, p_role, p_target_id)` зберігає свою
сигнатуру. Для `supplement` сервер перевіряє поле **питання**, а не поточне
налаштування групи й не константу 3. Невдалий перехід на інше місце
залишається атомарним: попередній запис не губиться.

Обидва шляхи збереження перевіряють усі вже зайняті `supplement`-місця,
включно з невидимими клієнтові записами. Зменшення нижче цього числа
відхиляє всю транзакцію. Однакове групове advisory-блокування захищає
зміну ліміту, збереження питання та запис учасника від гонок.

Збережені попередні перевірки основних місць і команд, незмінності
зарезервованих питань, часу початку заняття за Києвом, джерел розкладу,
групи й предмета, прав викладача, семестру, версії та повторного запиту.
Ротація основних відповідей залишається рекомендацією. Нових прав
прямого запису до таблиць міграція не додає.

## Помилки для інтерфейсу

| Код | Коли | Пояснення користувачеві |
| --- | --- | --- |
| `SEMINAR_SUPPLEMENT_CAPACITY_INVALID` | Невалідний параметр setter RPC. | «Оберіть від 0 до 30 місць для доповнювачів». |
| `SEMINAR_SUPPLEMENT_CAPACITY_BELOW_MEMBERS` | Новий ліміт питання менший за кількість записаних доповнювачів. | «Не можна встановити менше місць, ніж уже зайнято». |
| `SEMINAR_INVALID_INPUT` | Невалідне поле в масиві питань. | Наявна помилка валідації семінару. |
| `SEMINAR_TARGET_FULL` | Ліміт питання вичерпано або він дорівнює 0. | Наявне пояснення про відсутність вільних місць. |

Наявні помилки доступу, початку заняття й конфліктів залишаються чинними.

## Застосування

Міграція розрахована на поточні міграції семінарів, прав заступників,
рекомендації ротації, викладацького кабінету й проєкції розкладу
`202610160002_schedule_academic_projection.sql`. Вона перевіряє необхідні
сигнатури й актуальні контрольні фрагменти функцій. Кожен змінюваний
фрагмент має існувати рівно один раз; відмінність зупиняє всю транзакцію.
Повторне застосування навмисно зупиняється, щоб не замаскувати іншу схему
або історію міграцій. Власники, сигнатури й права виклику наявних функцій
зберігаються; новий setter дозволений лише `authenticated` і сам перевіряє
право групи.
