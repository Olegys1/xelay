# Сповіщення Xelay на пошту

Поштові сповіщення використовують Resend + наявний Supabase + Vercel. Без налаштувань нижче листи не надсилаються; особисті чати та інші можливості платформи продовжують працювати. Статус біля перемикача пошти показує готовність фонового обробника, а сам перемикач зберігає вибір користувача.

Підтвердження адреси й відновлення пароля надсилає **Supabase Auth через SMTP**. Дублювання сповіщень надсилають **серверні функції Xelay через Resend API**. Налаштування SMTP описано в окремій інструкції з автентифікації. Вимкнення звичайних сповіщень не блокує лист відновлення пароля.

## Оновлення політики: 14 жовтня 2026 — підготовлено до підключення

Нижче описана підготовлена нова версія. Цей документ сам по собі не підтверджує застосування міграцій або завершення Production-публікації; фактичні результати запуску потрібно записати окремо після підключення.

- Кожне довірене сповіщення платформи отримує **окреме завдання на лист**, навіть якщо сповіщення або повідомлення вже прочитано. Особисті повідомлення більше не об’єднуються; очікування п’яти хвилин, десятихвилинний інтервал чату та пропуск після 30 листів на користувача за годину прибрано.
- Поштове дублювання охоплює всі типи серверних сповіщень, зокрема питання та коментарі, запити на спілкування, особисті й групові чати, новини, навчальні групи, викладання та органайзери. Для майбутнього невідомого типу використовується загальний безпечний шаблон. Це не означає розсилку кожного перегляду сторінки або кожної технічної зміни.
- Додано самі сповіщення про зміни й видалення ДЗ, довгострокові завдання та їхні вкладення, матеріали, розклад, семінари, запрошення й завдання спільних органайзерів. Імпорт багатьох рядків розкладу та збереження питань одного семінару створюють одну подію для отримувача за операцію; готова подія все одно має свій окремий лист.
- **Явне вимкнення сповіщень/пошти, непідтверджена адреса та втрата доступу залишаються чинними обмеженнями.** Прочитання або прийняття запрошення не скасовує лист, якщо користувач зберігає необхідний доступ. Відхилене/відкликане запрошення, видалений приватний об’єкт, бан у приватному чаті або втрата членства перевіряються перед доставкою.
- Черга не розсилає історичні сповіщення й не повертає завершені `failed`, `skipped` або `sent` у розсилку. Зокрема, **108 раніше виявлених історичних завдань `failed` не реактивуються**. Живі `pending` з колишнім очікуванням прочитання/інтервалу чату можуть стати доступними раніше; для вже розпочатих невизначених спроб зберігається захист від повторної відправки.

## 1. Підготувати Resend

1. У Resend додайте власний домен `xelay.ink` або окремий піддомен для листів.
2. У панелі DNS вашого домену додайте саме ті записи, які покаже Resend. Дочекайтеся статусу Verified. Наявні записи для сайту не потрібно замінювати.
3. Для Xelay погоджено адресу `auth@xelay.ink`. Вона має належати підтвердженому в Resend домену. Якщо підтверджено лише піддомен, потрібна адреса цього піддомену.
4. Створіть API key з правом надсилати листи для цього домену. Запишіть його у Vercel, а не у фронтенд.

Звичайна тестова адреса Resend не придатна для листів усім користувачам. Для Supabase SMTP той самий сервіс має параметри: host `smtp.resend.com`, port `465`, username `resend`, password — API key. [Офіційна інструкція Resend для Supabase](https://resend.com/docs/send-with-supabase-smtp).

## 2. Додати змінні у Vercel

Відкрийте проєкт Xelay → Settings → Environment Variables. Для Production додайте:

```dotenv
SUPABASE_URL=https://ВАШ_ПРОЄКТ.supabase.co
SUPABASE_SERVICE_ROLE_KEY=СЕРВЕРНИЙ_КЛЮЧ_SUPABASE
XELAY_PUBLIC_URL=https://www.xelay.ink
RESEND_API_KEY=КЛЮЧ_RESEND
XELAY_EMAIL_FROM=Xelay <auth@xelay.ink>
NOTIFICATION_WEBHOOK_SECRET=ВЛАСНИЙ_ВИПАДКОВИЙ_СЕКРЕТ_32_СИМВОЛИ_АБО_БІЛЬШЕ
NOTIFICATION_EMAIL_ENABLED=true
```

`XELAY_EMAIL_FROM` повинен мати саме формат `Xelay <адреса@підтверджений-домен>`. Значення у панелі Vercel вводьте без лапок.

`NOTIFICATION_WEBHOOK_SECRET` — окремий випадковий пароль для зв’язку Supabase з Xelay. Використовуйте щонайменше 32 випадкові символи без пробілів. Він не є паролем користувача, API key Resend чи ключем Supabase.

Ключ `service_role` береться з серверних ключів вашого Supabase. Це **не** `anon` / `publishable` key. Існуючий `SUPABASE_SERVICE_ROLE` також підтримується, якщо вже використовується платіжним сервером. Жоден серверний секрет не повинен мати префікс `VITE_`.

Для Preview/Development залиште `NOTIFICATION_EMAIL_ENABLED=false`, щоб локальні перевірки не розсилали листи. Для нового підключення спочатку підготуйте Production змінні та базові залежності пошти. Для оновлення чинного Xelay порядок нижче обов’язковий: **новий серверний код перед міграціями 002 → 003 → 004**. Існуючі ключі Resend, Supabase та іншого фонового сервісу не потрібно замінювати.

## 3. Опублікувати сервер і виконати міграції в правильному порядку

Базова міграція `supabase/migrations/202610010004_email_notifications.sql` додає налаштування користувачів та захищену чергу `notification_email_outbox`. Попередня `supabase/migrations/202610070008_notification_email_unread.sql` і наявні міграції новин, навчальних груп, спільних органайзерів та викладання є залежностями нового оновлення. Не застосовуйте старі міграції повторно після нових: вони можуть повернути старі правила доставки.

Для оновлення вже підключеного Xelay:

1. **Спочатку опублікуйте новий серверний код** і дочекайтеся Ready у Production Vercel. Старий сервер після нових міграцій міг би пропускати вже прочитані події або неправильно обробляти нові типи сповіщень. Новий сервер до готовності SQL-пакета не читає завдання старої черги й показує `unavailable`.
2. Застосуйте **один атомарний SQL-пакет** у порядку **002 → 003 → 004**:
   - `supabase/migrations/202610140002_all_notification_email.sql`: окремі негайно доступні листи для всіх типів подій, без фільтра прочитання, об’єднання особистого чату та погодинного пропуску; надійне очікування квоти провайдера.
   - `supabase/migrations/202610140003_academic_notification_producers.sql`: нові навчальні та командні події, правильний автор редагування ДЗ, аудиторія з прийнятими учасниками й старостою, приватний контекст спільного органайзера.
   - `supabase/migrations/202610140004_chat_notification_email_context.sql`: приватний контекст групових і факультетських чатів.
3. Пакет має одну зовнішню `BEGIN;` / `COMMIT;`. Під час складання прибираються **тільки окремі зовнішні рядки `begin;` і `commit;` кожного файлу**; тіла функцій, перевірки залежностей і всі інші інструкції зберігаються. Не склеюйте оригінальні файли з їхніми внутрішніми транзакціями: це порушить атомарність. Якщо будь-яка частина пакета не застосована, вся транзакція відкотиться.
4. Перевірте справжні запуски хвилинного обробника, публічний статус, стан квоти та нову погоджену тестову подію. Після успішної перевірки запишіть ідентифікатор deployment і результати нижче.

Службовий статус SQL підтверджує `delivery_mode='per_notification_v1'` і `contexts_ready=true` лише за наявності обох нових функцій перевірки приватного контексту. Обробник і публічна готовність потребують цих ознак. Це захищає період між публікацією сервера та завершенням атомарного SQL-пакета.

Кожна нова міграція виконується в транзакції й має перевірки залежностей. Нові міграції не створюють історичних листів і не виконують повторний `email_setup_cutover`. Під час підключення 7 жовтня цей код уже зберіг 565 старих завдань як `skipped`; ця історія залишається без розсилки. Нові завдання створюються лише за умови підтвердженої адреси й увімкнених налаштувань.

Звичайний користувач не може додати в чергу довільну адресу чи текст. Для перевірки приватних чатів та спільних органайзерів сервер використовує `xelay_chat_notification_email_context(job_id,lock_token)` і `xelay_shared_organizer_notification_email_context(job_id,lock_token)`. Їх може викликати лише `service_role` з чинною двохвилинною орендою конкретного завдання. Відповідь містить тільки дозвіл, безпечний код причини та посилання; **нових прав `SELECT` на приватні таблиці чатів або органайзерів не надається**.

## 4. Створити Database Webhook

У Supabase знайдіть **Database Webhooks** → Create webhook:

| Поле | Значення |
| --- | --- |
| Name | `xelay-notification-email` |
| Schema | `public` |
| Table | `notification_email_outbox` |
| Events | тільки `INSERT` |
| Method | `POST` |
| URL | `https://www.xelay.ink/api/notifications/email` |
| Header `Content-Type` | `application/json` |
| Header `Authorization` | `Bearer ВАШ_NOTIFICATION_WEBHOOK_SECRET` |

Після `Bearer` має бути один пробіл. Значення секрету повинно збігатися з Vercel. Подію `UPDATE` вмикати не потрібно: вона створила б зайві виклики після оновлення стану черги.

У полі timeout, якщо воно доступне, встановіть `55000` мс. Публічна Production адреса повинна відкриватися без захисту паролем Vercel. Сервер сам перевіряє секрет. URL локального Vite `127.0.0.1` для цього webhook не підходить.

Database Webhook передає подію асинхронно після зміни рядка. [Документація Supabase](https://supabase.com/docs/guides/database/webhooks).

## 5. Підключити повторні спроби

Цей крок потрібен: якщо webhook або поштовий сервіс тимчасово не відповідає, черга повинна мати повторний запуск.

1. У Supabase увімкніть розширення **pg_net**, **pg_cron** та **Vault**, якщо їх ще немає.
2. У Vault через його інтерфейс створіть два секрети:
   - Name `xelay_public_url`, value `https://www.xelay.ink`.
   - Name `xelay_notification_webhook_secret`, value — той самий секрет, що у Vercel.
3. Відкрийте `supabase/setup/notification_email_retry.sql`, скопіюйте весь його вміст у SQL Editor та натисніть Run. У файл нічого додавати не потрібно: він читає значення з Vault.

Створиться задача `xelay-notification-email-retry` раз на хвилину. Повторне виконання setup оновлює цю ж задачу. Вона викликає `/api/notifications/retry` навіть за порожньої черги: успішний запуск оновлює службову позначку працездатності. Новий обробник перевіряє **до 80 завдань послідовно за виклик**, з паузою 300 мс між ними та окремим обмеженням часу на кожне. За повільних відповідей, глобальної паузи або вичерпання бюджету часу обробляється менше; виклик завершується в межах 60 секунд. Число 80 не є гарантією кількості надісланих листів. [Планування викликів із Vault у Supabase](https://supabase.com/docs/guides/functions/schedule-functions).

Після запуску зачекайте до двох хвилин. `GET /api/notifications/email` повертає лише `{available,state}`. Стан `ready` потребує коректних серверних налаштувань і успішного запуску обробника не більш ніж 180 секунд тому. `not_configured` означає відсутні налаштування, `limited` — паузу через денну/місячну квоту Resend, `unavailable` — непідтверджену поточну роботу або іншу паузу провайдера. Статус не розкриває ключів, адрес, черги чи деталей помилок; він не гарантує потрапляння конкретного листа у Inbox.

Для тимчасової зупинки листів встановіть `NOTIFICATION_EMAIL_ENABLED=false` у Vercel й повторно розгорніть проєкт. Для зупинки самої задачі виконайте:

```sql
select cron.unschedule('xelay-notification-email-retry');
```

## Як працює доставка

- В адресатах використовується підтверджена адреса **Supabase Auth**, а не редаговане поле профілю.
- Перед надсиланням повторно перевіряються поточні налаштування. Вимкнення всіх сповіщень або лише листів пропускає завдання, що ще очікують. Вже надісланий лист відкликати неможливо.
- Лист містить загальний український опис події та посилання на Xelay. Текст приватного повідомлення, домашнього завдання, вкладення чи контактні дані в лист не копіюються.
- У листі є «Керувати сповіщеннями». На платформі налаштування відкриваються через дзвіночок. Авторизація на платформі все одно потрібна для перегляду приватних даних.
- Кожне сповіщення, включно з окремими повідомленнями тієї самої розмови та власним нагадуванням органайзера, має незмінне окреме завдання `notification:<id>`. Прочитані `notifications.is_read` і `messages.read_at` не впливають на доставку; очікування п’яти хвилин та десятихвилинний інтервал прибрано.
- Перед доставкою перевіряються актуальні отримувач, повідомлення, прийнятий запит на спілкування та доступ до приватного об’єкта. Прийняття запрошення не скасовує лист за збереженого доступу; видалення повідомлення, сповіщення або втрата доступу можуть скасувати його. Посилання веде у відповідну розмову, групу або органайзер; потрібен вхід у Xelay.
- Погодинного пропуску після 30 листів немає. Ліміт провайдера не видаляє решту подій: вони очікують у черзі під час загальної паузи.
- Повторні спроби використовують той самий `Idempotency-Key`, максимум п’ять спроб доставки. Вікно 23 години починається з **першої спроби доставки**, а не з дати створення ще не обробленого завдання. Завдання без спроб можуть чекати квоти; невизначені попередні відправки не повторюються за межами безпечного вікна. [Resend зберігає ключ захисту від повторної відправки 24 години](https://resend.com/docs/dashboard/emails/idempotency-keys).
- Стан `sent` означає, що Resend **прийняв** лист, а не підтвердження читання чи гарантоване потрапляння у Inbox. Відхилення адресою / Spam перевіряються в панелі Resend.

### Квота й загальна пауза

На перевіреному тарифі Resend Free діє **100 листів на день на акаунт**, а не 100 на кожного користувача. Це обмеження провайдера; збільшення швидкості обробника його не змінює. Інші відправки цього акаунта, зокрема SMTP-пошта Auth, також потрібно враховувати. Для масового дублювання кожної події потрібна відповідна квота Resend. [Ліміти надсилання Resend](https://resend.com/docs/knowledge-base/resend-sending-limits).

У разі чіткої відмови через денну/місячну квоту, частоту запитів або конфігурацію завдання залишається `pending`, а обробник зберігає `paused_until` і `pause_reason` для всієї черги. Денна пауза — до наступної доби UTC плюс п’ять хвилин, місячна — на 24 години, частота запитів — на хвилину, конфігурація — на десять хвилин. Після відновлення обробка продовжується. Успішний heartbeat не скидає цю паузу; кожна подія не повторює один і той самий запит до вичерпаної квоти.

Однозначна відмова провайдера під час першої спроби не витрачає ліміт повторних спроб і не запускає вікно невизначеної доставки. Якщо попередня спроба вже могла бути прийнята, її початковий час зберігається, щоб не створити дубль.

## Перевірка після підключення

Спочатку перевірте `GET /api/notifications/email`, успішні HTTP-відповіді хвилинної задачі та відсутність старих завдань у розсилці. Позначку працездатності вручну не оновлюйте: її створює реальний обробник.

За погодженням власників двох тестових акаунтів з підтвердженими адресами перевірте окремі листи для кількох повідомлень однієї розмови, зокрема після прочитання повідомлення й відкриття дзвіночка. Затримки п’яти/десяти хвилин бути не повинно, але фактична доставка залежить від черги, доступності сервісів і квоти. Перевірте посилання в конкретну розмову, навчальну групу та спільний органайзер. Після вимкнення «Сповіщення на пошту» новий лист не повинен надходити. Окремо перевірте, що втрата членства закриває приватні посилання й скасовує доставку, а прийняття запрошення за збереженого доступу не скасовує її. Відновлення пароля залишається окремим сценарієм Auth.

Для перегляду станів без адрес і текстів:

```sql
select id, status, attempts, created_at, last_error_code
from public.notification_email_outbox
order by created_at desc
limit 30;
```

| Стан / код | Що перевірити |
| --- | --- |
| `pending` довго не змінюється | Database Webhook, cron, Production deployment, серверні змінні; також `paused_until` і квоту Resend |
| `processing` понад 2 хвилини | Повторний запуск поверне завдання після завершення блокування |
| `skipped` / `notifications_disabled` | Користувач вимкнув сповіщення або листи |
| `skipped` / `email_unverified` | Пошта не підтверджена |
| Історичний `skipped` / `already_read` | Запис старої політики; нова версія не пропускає лист через прочитання |
| `skipped` / `message_removed`, `connection_removed`, `group_access_removed`, `chat_access_removed`, `organizer_membership_removed` | Приватний об’єкт видалено або актуального доступу вже немає |
| `skipped` / `email_setup_cutover` | Історичне завдання збережене без розсилки при підключенні |
| Історичний `read_delay` / `conversation_rate_limit` | Колишнє очікування чату; нові події його не використовують, живі завдання міграція розблоковує без реактивації завершеної історії |
| `pending` / `provider_daily_quota`, `provider_monthly_quota` | Загальна пауза до відновлення квоти; публічний статус `limited` |
| `pending` / `provider_rate_limit` | Тимчасова загальна пауза через частоту запитів |
| `pending` / `provider_configuration` | API key, підтвердження домену або адресу відправника; черга збережена під час паузи |
| `failed` / `provider_401`, `provider_403`, `provider_429` у старій історії | Історична помилка провайдера; автоматично не реактивується |
| `failed` / `provider_409` | Зміна адреси/конфігурації між повторними спробами; новий ключ автоматично не створюється |

Опис помилок провайдера: [Resend API errors](https://resend.com/docs/api-reference/errors). Секрети й адреси користувачів у публічні скриншоти та Git не додавайте.
