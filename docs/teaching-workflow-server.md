## Заплановані публікації

### Поля TypeScript / JSON

```ts
type TeachingSubmissionFormat = 'written' | 'oral' | 'defense'
type TeachingPublicationStatus = 'draft' | 'scheduled' | 'published'

// Додаються до наявної TeachingPublication:
status: TeachingPublicationStatus
publish_at: string | null       // ISO timestamptz; лише scheduled
submission_format: TeachingSubmissionFormat

type TeachingScheduledPublication = TeachingPublication & {
  course_id: string
  course_title: string
  kind: 'assignment' | 'material'
  schedule_error?: string | null
  schedule_checked_at?: string | null
}
```

`scheduled_by` встановлює сервер; клієнт не обирає автора запланованої дії.
Для матеріалів допустимий лише `submission_format='written'`, оскільки
формат студентської відповіді до них не застосовується.

Збереження відбувається через попередні дії:

* завдання групи: `xelay_classroom_mutate('save_group_assignment', payload)`;
* матеріал: `xelay_teaching_mutate('save_material', payload)`.

Для планування передаються `status: 'scheduled'` і `publish_at` — скінченний
момент у майбутньому. Решта перевірок редактора, семестру, ресурсів, груп,
предмета та пар залишається чинною. Відмітка дати пари або дедлайну сама по
собі не планує публікацію. Матеріал потребує такого самого явного підтвердження
умов розміщення, як негайна публікація; час згоди фіксується при плануванні.
Раніше опублікований запис не можна перетворити на нову заплановану публікацію.

```ts
supabase.rpc('xelay_teaching_scheduled_items', { p_group_id: groupId ?? null })
// { items: TeachingScheduledPublication[] }
```

Список містить лише заплановані записи з актуальним правом редагувати їхній
тип у неархівному предметі. Для матеріалу додатково потрібне авторство.
Фільтр групи не відкриває сторонні предмети. `schedule_error` — короткий
серверний код останньої невдалої спроби, без приватного вмісту робіт або шляхів.
Після редагування стара помилка очищається.

Скасування не видаляє матеріал, файл або завдання:

```ts
repository.mutate('cancel_scheduled_publication', {
  id: itemId, course_id: courseId, version: itemVersion,
  request_id: operationUuid,
})
// { id, version, status: 'draft' }
```

`request_id` — новий UUID для окремої операції; повтор того самого запиту
використовує той самий UUID і payload. Виконується перевірка версії й прав;
чужий матеріал скасувати не можна. Паралельна публікація або редагування
призведе до конфлікту версії, а не до прихованого перезапису.

### Серверний запуск без ноутбука

Роботу виконує **pg_cron усередині наявного Supabase Postgres**. Це не локальний
процес, не сторонній платний планувальник і не браузерна вкладка. Нова послуга
для цього не підключається; використовуються ресурси чинної бази.

1. Оператор перевіряє доступність розширення pg_cron у своєму Supabase-проєкті.
2. Якщо його ще немає, вмикає pg_cron / Supabase Cron у налаштуваннях розширень.
   SQL-варіант для підтримуваного проєкту від `postgres`:

   ```sql
   create extension if not exists pg_cron with schema pg_catalog;
   ```

3. Якщо pg_cron було встановлено **до** 003, міграція встановлює задачу сама.
   Якщо розширення ввімкнули пізніше, оператор викликає:

   ```sql
   select public.xelay_install_teaching_publication_cron();
   ```

4. Від `postgres` перевіряє канонічний job:

   ```sql
   select jobid, jobname, username, database, schedule, active, command
   from cron.job where jobname='xelay-teaching-publications';
   ```

Задача викликає `xelay_publish_due_teaching_items()` щохвилини. Публікація
відбувається на першій успішній спробі після обраного моменту, а не з гарантією
точності до секунди. Пауза або недоступність самої бази відкладає запуск.
Якщо правильного активного job немає, нове планування відхиляється з
`TEACHING_SCHEDULER_UNAVAILABLE`; звичайні чернетки та негайна публікація працюють.

Worker і installer закриті від браузерних ролей та `service_role`; навіть
отриманий випадково EXECUTE не обійде перевірку сесії `postgres`. Worker має
окреме advisory-блокування від паралельного запуску, обробляє до 100 записів
за один запуск і повторно перевіряє:

* статус, актуальну версію та час запису;
* активний предмет і чинні права автора та того, хто запланував дію;
* усі прийняті підключення цільових груп;
* відповідність предмета, дати й вибраної пари актуальному розкладу;
* авторське підтвердження матеріалу;
* існування, власника і збережені MIME/розмір приватних файлів.

На час перевірки й публікації блокуються відповідні записи Auth, профілю та
підтвердження викладача. Конкурентне блокування акаунта, зміна факультету чи
відкликання підтвердження не може пройти між перевіркою прав і публікацією.
Ці блокування беруться з `NOWAIT`: зайнята зміною акаунта стрічка відкладає
конкретний запис, не створюючи взаємного очікування з видаленням акаунта.

Після успіху в одній транзакції змінюється статус, створюється/оновлюється
колонка оцінювання завдання та через наявний механізм надходять сповіщення.
До цього студентські RPC, проєкції матеріалів/розкладу, widgets і підписування
файлів продовжують вимагати `status='published'`. Чернетки й scheduled-записи
не створюють студентських сповіщень або email. Свідомо передане викладачем
посилання чи раніше виданий signed URL має власний строк дії, як і раніше.

Помилка одного запису відкочує його публікацію та не зупиняє наступні записи.
Вона зберігається у приватній таблиці; повторна спроба — не раніше ніж через
5 хвилин. Невдала перевірка прав не розширює доступ автоматично.

## Формат відповіді та оцінки

`written` — звичайна письмова відповідь; для фінальної здачі потрібні текст,
посилання або файл. `oral` і `defense` — позначення формату: фінальну відповідь
можна надіслати без файла та без тексту. Вони не додають прихованого стану
«захист пройдено». Окремої дії `record_defense` цей контракт не створює.

Будь-який із форматів можна оцінювати без студентської submission через
існуючий журнал. Для цього не перевіряються захист, запис на семінар,
наявність файла або вибір питання. Новий семестр і копіювання завдання
зберігають формат, але не запускають старий план публікації.

## Дедлайн і завершення приймання

```ts
type TeachingTarget = ExistingTeachingTarget & {
  closes_at?: string | null
}
```

`due_at` залишається дедлайном для позначки **late**. `closes_at` — окремий,
необов'язковий момент, після якого сервер відхиляє **фінальну здачу**.
Якщо вказано обидва моменти, `closes_at >= due_at`. Обидва — ISO timestamptz;
інтерфейс показує та вводить київський час, як чинний `kyivDeadline()`.

Після завершення приймання можна зберігати приватну чернетку; викладач може
перевіряти, повертати роботу та виставляти бали. Повернення на доопрацювання
саме по собі не продовжує cutoff: потрібне явне продовження. Доступ до групи,
архів предмета та статус завдання перевіряються незалежно.

Відповідь `xelay_classroom_assignment(item, group)` додає:

```ts
effective_closes_at: string | null // для поточного користувача
is_closed: boolean
can_save_draft: boolean
can_submit: boolean               // false після cutoff
submission_extensions: {
  item_id: string; group_id: string; user_id: string
  closes_at: string | null; version: number
}[]                               // тільки assignments-editor
```

Кожен елемент `students` і `submissions` також містить `effective_closes_at`,
`extension_version` (0, якщо запису ще немає) та `extension_closes_at`.
Студент не отримує extensions інших людей. Нова спроба отримує фактичний
серверний `submitted_at`, щоб позначка late не залежала від часу початку запиту.

### Індивідуальне продовження

```ts
repository.classroomMutate('set_submission_extension', {
  id: operationUuid,               // UUID операції, НЕ id студентської submission
  request_id: operationUuid,       // необов'язково; якщо є, має збігатися з id
  version: extensionVersionOrZero,
  item_id: itemId, group_id: groupId, user_id: studentId,
  closes_at: newIsoInstantOrNull,
})
// { id, version, item_id, group_id, user_id, closes_at, effective_closes_at }
```

Потрібні актуальне право `assignments`, неархівний предмет, прийнята група,
опубліковане завдання цієї групи та членство студента. Доступ лише до журналу
не дає права змінювати приймання робіт. Рішення записується в приватну історію,
а студенту надходить сповіщення.

Override може тільки продовжити наявний груповий cutoff. Якщо груповий cutoff
відсутній, приймання необмежене; індивідуальне обмеження не створюється.
Ефективний час — максимум актуального групового cutoff та продовження.
`closes_at:null` знімає override, залишаючи версійований tombstone, щоб не
зламати захист від застарілого збереження. Групова зміна строку не може
перетворити продовження на коротший персональний строк.

Збереження старим клієнтом без `target.closes_at` зберігає наявний cutoff.
Явний `null` його прибирає. Відокремлення спільного завдання для тієї самої
групи переносить cutoff, індивідуальні продовження й історію разом із роботами
та балами. Незалежна копія для іншої групи або новий семестр їх не успадковує.

## Прохання перевірити результат

```ts
type TeachingGradeRequest = {
  id: string; course_id: string; course_title: string
  group_id: string; group_name: string
  activity_id: string; activity_title: string
  entry_id: string; user_id: string; student_name: string
  message: string; status: 'open' | 'resolved'; response: string
  created_at: string; resolved_at: string | null; resolved_by: string | null
  version: number; can_manage: boolean; can_resolve: boolean
}

supabase.rpc('xelay_teaching_grade_requests', { p_course_id: courseId ?? null })
// {
//   requests: TeachingGradeRequest[],
//   available_activities: {
//     activity_id, activity_title, activity_date, course_id, course_title,
//     group_id, group_name, max_points
//   }[]
// }
```

Студент бачить тільки свої звернення й доступні активності власного активного
запису журналу в прийнятій групі. `available_activities` працює також тоді,
коли жодного балу ще немає. Звичайна самостійна колонка журналу вже видима
за чинним контрактом; колонка з `item_id` доступна тут тільки для опублікованого
завдання. Назви/зміст draft або scheduled-завдання через цей список не відкриваються.

Викладач із поточним `grades` бачить звернення відповідного предмета й
прийнятих підключених груп. `can_resolve` обчислюється для кожного звернення
окремо; `can_manage` позначає поточне право журналу і дозволяє показувати
викладачеві також уже розглянуті звернення. Статус викладача іншого предмета
не дає кнопки відповіді. Для викладача
без власного студентського запису порожній `available_activities` нормальний.
Приватні роботи, файли й чужі бали ці RPC не повертають.

```ts
supabase.rpc('xelay_teaching_request_grade', {
  p_activity_id: activityId, p_message: message, p_request_id: operationUuid,
})
// { id, version, status, existing: boolean }

supabase.rpc('xelay_teaching_resolve_grade_request', {
  p_request_id: gradeRequestId, p_version: version, p_response: response,
})
// { id, version, status: 'resolved' }
```

Повідомлення — 2..1000 символів після обрізання пробілів, відповідь — 2..2000.
Одночасно існує лише одне відкрите звернення студента до однієї активності.
Повторний новий UUID для вже відкритого звернення повертає його, не змінюючи
текст і не надсилаючи повторного сповіщення.
`existing:true` явно повідомляє, що повернуто попереднє відкрите звернення,
тому новий текст не записано; для створеного звернення повертається `false`.
Ретрай того самого UUID з іншим
payload дає конфлікт; повтор повертає історичний результат операції, а не
актуальний стан після втрати доступу до групи. Обмеження нових звернень — 10 за годину, 30 за добу,
повтор до тієї самої активності — не частіше разу на добу. Нові UUID-ретраї
теж обмежені: до 60 за годину та 200 за добу.

Відповідь вимагає чинного `grades`, активного предмета та прийнятої групи,
перевіряє версію і створює приватну історію дії. Повтор тієї самої відповіді
того самого викладача не створює другого сповіщення. Відповідь на звернення
**не виставляє й не змінює бал автоматично**. Для оцінювання використовується
чинний журнал незалежно від наявності звернення, submission або захисту.

## Нові коди помилок

| Код | Значення |
| --- | --- |
| `TEACHING_SCHEDULER_UNAVAILABLE` | Немає правильного активного серверного job; планування недоступне. |
| `TEACHING_SCHEDULE_TIME_INVALID` | Час публікації відсутній, нескінченний або вже минув. |
| `TEACHING_PUBLISHED_CANNOT_SCHEDULE` | Цей запис уже публікували; створіть нову заплановану публікацію. |
| `TEACHING_NOT_SCHEDULED` | Запланований стан уже змінився. |
| `CLASSROOM_SUBMISSIONS_CLOSED` | Груповий або ефективний індивідуальний cutoff минув. |
| `TEACHING_EXTENSION_INVALID` | Продовження не є скінченним або скорочує/створює відсутній cutoff. |
| `TEACHING_GRADE_REQUEST_INVALID` | Невалідний ідентифікатор, версія або довжина повідомлення/відповіді. |
| `TEACHING_GRADE_REQUEST_ENTRY_REQUIRED` | Немає власного активного запису журналу цієї групи/предмета. |
| `TEACHING_GRADE_REQUEST_RATE_LIMIT` | Уже є недавнє звернення або досягнуто обмеження частоти. |

Існуючі `TEACHING_CONFLICT`, помилки доступу, матеріальних прав, ресурсів,
прив'язки до пари й архіву зберігають свою семантику.

## Перевірка джерел перед застосуванням

Для точного порівняння використано base64-експорт `pg_get_functiondef`, оскільки
текстове відображення результату може змінювати відступи. Послідовне порівняння
22 основних і 4 copy-якорів пройшло 26/26 на точних джерелах, для LF і CRLF.
Міграція симетрично видаляє CR із тіла функції та old/new літералів редактора;
інші символи й очікувана кількість збігів залишаються суворо перевіреними.
Без цієї симетрії CRLF редактора відтворює відмову на багаторядковому якорі 7.
Це офлайн-порівняння джерел, воно не є підтвердженням застосування міграції.
